# Application Gateway - Global configurations

Azure Application Gateway global configuration settings apply to the entire gateway. Before changing these settings, consider their potential impact on traffic, service availability, and billing.

This article describes the settings available on the Configuration blade in the Azure portal.

## Tier

The Tier setting determines the SKU of your Application Gateway resource. Selecting a different tier might affect the cost of your deployment. Review [Application Gateway pricing](https://azure.microsoft.com/pricing/details/application-gateway/) before selecting a tier.

## Capacity type

### Autoscale

Automatically adjusts the number of Application Gateway instances based on traffic demand. Specify the [minimum and maximum instance](https://learn.microsoft.com/azure/well-architected/service-guides/azure-application-gateway#configuration-recommendations-4) counts to control its scaling. 

### Manual

Allows you to specify a fixed number of Application Gateway instances. The instance count remains unchanged unless you manually update it.


## HTTP/2

Application Gateway supports HTTP/2 for communication between clients and the gateway, improving performance through features such as request multiplexing and header compression. HTTP/2 is supported only on frontend connections, while communication with backend servers uses HTTP/1.1. You can enable or disable HTTP/2 during gateway creation or update this setting later.

## FIPS (Federal Information Processing Standard) mode 140-2

FIPS mode enables Application Gateway V2 to use FIPS 140 validated cryptographic modules for encryption, hashing, and signing operations. When enabled, Application Gateway supports only FIPS-compliant TLS policies and cipher suites. FIPS mode is optional in Azure Public Cloud and enabled by default for deployments through the Azure portal in Azure Government. To learn more, see [FIPS mode in Application Gateway](./fips.md).


## Server information

You can control whether Application Gateway identifies itself in the `Server` response header and on its default error pages. When enabled, Application Gateway includes `Microsoft-Azure-Application-Gateway/v2` in the Server response header and identifies itself on default error pages. This information can help you identify responses generated by Application Gateway during troubleshooting, especially in architectures that use multiple proxies or load balancers. In these architectures, it can be challenging to determine which component generated a response. You can disable this information to reduce the exposure of infrastructure details to clients.

Configure this setting on the gateway by using the Azure portal, Azure PowerShell, or the REST API.

### Azure portal

1. In the Azure portal, open your Application Gateway resource.
2. Under **Settings**, select **Configuration**.
3. Set **Application Gateway server information** to **False** to prevent Application Gateway from identifying itself in responses. Set it to **True** to include the information.
4. Select **Save**.

### Azure PowerShell

To disable Application Gateway server information on an existing gateway, set the `DisableDefaultServerHeaderInResponse` property to `$true` and update the gateway:

```azurepowershell-interactive
$appgw = Get-AzApplicationGateway -Name "<application-gateway-name>" -ResourceGroupName "<resource-group-name>"
$appgw.DisableDefaultServerHeaderInResponse = $true
Set-AzApplicationGateway -ApplicationGateway $appgw
```
